# Object-Centric Event Log Abstraction and Case Extraction Through Mereotoplogy

Reference implementation of the theory of applied process mereotoplogy from *Through the Object-Centric Looking Glass: a Mereotopology-based Foundation for Transparent Event Log Abstraction and Case Extraction*. Given an OCEL (object-centric event log) in DuckDB and a domain theory — which object types are identity-bearing (𝔅) and which types connect — it compiles a fixed [Soufflé](https://souffle-lang.github.io/) Datalog program that computes the resulting executions: the connected sums (wholes) of events fused by shared or co-participating identity-bearing objects. It also reports the correctness-relevant byproducts of that computation — ambiguous (indeterminate) events and overlap between executions.

## The mereotopology, briefly

Mereotopology is the study of *part* and *connection*. The paper reads both relations off the log directly:

- **Part** (`part`): an event is an atomic part of the execution it belongs
  to, the ordinary sense of "part of a whole" — reflexive (an event is part
  of itself), antisymmetric, transitive.
- **Connection** (`C`): two events are connected when an identity-bearing
  object participates in both directly, or when a declared pair of types
  (`--connect A:B`) co-participate — an `A` in one event and a `B` in the
  other, tied together through a shared event where both show up.
- **Sum/fusion**: an execution is the *sum* of every event connected, through
  a chain of such connections, to a given identity-bearing object — the
  whole generated by that object's participation history.

Concretely: `--identity order` makes each order's participation history the seed of an execution. `--connect order:container` extends that execution to every event a co-participating container also touches, and transitively to whatever those events connect further. An object type left undeclared (a resource, like a forklift or truck) can still sit inside an execution's events without ever seeding or extending one itself.

## Requirements & Running

It is recommend to use the [devcontainer setup for the Ontology-Driven Process Analysis Library (OPAL)](https://github.com/Ontology-Benchmarks/OPAL-devcontainer/tree/main)

This container contains everything needed to run the theory and mapping, including the virtual knowledge graph implementation, the datalog reasoner, and the base python environment and libraries. The web-based front-end is still a work-in-progress and is not necessary, usage through the CLI is described below. 


## Usage

```
python ocel_to_datalog.py LOG.duckdb --out DIR --identity TYPE \
    [--connect A:B ...] [--rename OLD:NEW ...] [--name NAME] [--run]
```

- `LOG.duckdb` — a DuckDB file containing a `log_e2o(eid, object_type,
  object_id)` table (the event-to-object relation of the log, as produced by the OPAL mapping of the OCEL2 log).
- `--out DIR` — output directory; `facts/` and (with `--run`) `output/` are
  created inside it.
- `--identity TYPE` — declares `TYPE` identity-bearing (𝔅 in the paper): its
  objects generate executions and propagate identity through determinate
  co-participation (repeatable).
- `--connect A:B` — a `TypeConn(A, B)` declaration: co-participation of an
  `A` and a `B` connects the events each participates in. Any type named here
  that isn't also declared `--identity` is a connector — it can carry an
  execution's identity across events without itself being identity-bearing
  (repeatable).
- `--rename OLD:NEW` — rename an object type from the log before processing
  (repeatable).
- `--name NAME` — base name for the generated `.dl` file; defaults to the
  DuckDB file's stem.
- `--run` — also invoke `souffle` on the generated program and write CSV
  results to `DIR/output/`.

This writes `DIR/<name>.dl` (the Datalog program) and `DIR/facts/*.facts`
(the log encoded as Soufflé input relations). Re-running the script only
regenerates the facts/program — the Datalog rules themselves are a fixed
template (see `TEMPLATE` in [ocel_to_datalog.py](ocel_to_datalog.py)). This template corresponds to the axiom schema of the mereotopology with the foundational mereotoplogy axioms pre-pended. 

## Examples

[ocel_examples/](ocel_examples/) holds one subfolder per sample log. Each log subfolder contains the source `mapped_log.duckdb` plus one or more generated runs:

```
ocel_examples/<log>/
  mapped_log.duckdb       # source OCEL log
  gen[_variant]/          # one folder per run of ocel_to_datalog.py
    <name>.dl             # generated Soufflé program
    facts/                # generated input facts (.facts files)
    output/                # Soufflé results (.csv), present when run with --run
```

| Log | Run folder | Identity-bearing types (𝔅) | Connectors |
|---|---|---|---|
| `bpi17` | `gen/` | `application` | `offer`, `workflow` |
| `logistics` | `gen_order/` | `order` | `container`, `transport_document` |
| `logistics` | `gen_sym/` | `container`, `order`, `transport_document` | — |
| `order_mgmt` | `gen/` | `orders` | `items`, `packages` |
| `p2p` | `gen/` | `purchase_requisition` | `goods_receipt`, `invoice_receipt`, `material`, `payment`, `purchase_order`, `quotation` |

`logistics` has two runs over the same log to show how the choice of domain
theory changes the resulting executions: `gen_order` makes only `order`
identity-bearing (so containers and transport documents fuse into whichever order they connect to), while `gen_sym` makes `container`, `order`, and `transport_document` identity-bearing symmetrically, so each generates its own execution unless fused by a shared connector.

To regenerate an example, e.g. `bpi17`:

```
python ocel_to_datalog.py ocel_examples/bpi17/mapped_log.duckdb \
    --out ocel_examples/bpi17/gen --identity application \
    --connect application:offer --connect application:workflow --run
```

Each run's `.dl` header comment records the exact 𝔅/connector types used —
the source of truth if you want to reproduce a run exactly (the `--connect`
pairs themselves aren't recoverable from it, only the resulting type sets).
